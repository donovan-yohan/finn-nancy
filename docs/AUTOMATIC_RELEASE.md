# Automatic qualified image publication

The repository owner's merge of a PR into protected `main`, followed by successful exact-main `ci.yml` push CI, authorizes automatic qualification and publication. This is owner approval, not an independent reviewer attestation. GitHub does not allow authors to approve their own PRs. Configure required PRs, the GitHub Actions `deterministic harness` check, up-to-date branches, conversation resolution, administrator enforcement, and no force pushes/deletion; zero required approving reviews supports a solo owner.

The `release image` workflow listens for successful main CI completion. It checks out only the trusted default-branch workflow revision, requires that revision to equal the triggering CI head and current remote main, and binds the source tree to an owner-merged PR. Failed CI, fork/PR runs, direct pushes, non-owner merges, stale main and mismatched trees refuse. Squash merges with a matching reviewed head tree are supported. A source advancing during qualification can conservatively cancel publication; the latest successful main CI gets its own attempt.

Qualification retains the existing native build/smoke and separate package-write publication jobs. Manual dispatch with the original independent-review attestation remains available. Automatic release authority is recorded honestly as `owner_merge_and_successful_main_ci`; its SHA-256 is an integrity digest of GitHub evidence, not a fabricated independent review.

After verified publication, a separate contents-write `announce` job uses a pinned GitHub provenance action (scoped `id-token: write` and `attestations: write`) to sign the canonical receipt, then publishes a GitHub release named `deploy-<source SHA>` with `release.json` and `release.sigstore.json`. Consumers must cryptographically verify the receipt against its exact source/signer digest, main ref, named release workflow and GitHub-hosted runner identity using the public signature bundle; image-provided labels alone do not prove workflow provenance. This asset contains only source commit/tree, immutable image reference, platform, PR number and workflow run/attempt. It never contains runtime paths, configuration, credentials, financial state, raw logs or full receipts. Only automatic releases become the public deployment feed. The original manual flow remains unannounced. An announcement failure does not undo a registry push; duplicate release tags are refused rather than overwritten.

A separately installed guest-side consumer may poll the public latest release asset without receiving CI credentials or granting CI production access. It must independently check GitHub run/PR/tree/main evidence and exact schema, validate the image digest and platform, and use a pinned state-preserving executor. No production caller is installed or enabled by this application PR. Changing deployed executor code remains a separate reviewed operation.

The one-shot qualification/publication receipt tests retain generated boundaries; hosted CI and a real automatic release are required before claiming end-to-end automation. No new release automatically enrolls bank accounts, changes provider credentials or resets application state.
