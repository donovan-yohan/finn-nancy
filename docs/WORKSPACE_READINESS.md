# Household workspace readiness

## User outcome

Finn Nancy is ready when one application supports household bank onboarding, transaction and spending review on desktop and mobile, and Namako's expense categorization and financial queries through a supported CLI or API.

A polished isolated sandbox is not this outcome. Production readiness requires the bank-feed, canonical ledger, categorization and reporting paths to meet at tested boundaries.

## Acceptance

- Every application page uses the shared black/white neutral theme, accessible blue bookkeeping and orange category/planning accents, compact spacing and consistent navigation.
- Home shows period-scoped financial summaries linked to contributing transactions. Unknown accounting meaning and incomplete data remain visible without inventing income or spending.
- Activity supports search, dates, account and category filters, precise signed money, row details and reachable actions at phone and desktop widths. Pagination must preserve filters.
- Each household member can connect their own institution with fresh consent. Connection ownership, account inclusion and personal/shared ownership are distinct. Add, repair, sync and disconnect have recoverable outcomes.
- Plaid ingestion is idempotent across retries, pending replacements, modifications and removals. Receipts and bank statements do not create duplicate expenses. Provider category suggestions do not silently become approved accounting categories.
- Namako has a documented remote machine-readable query and categorization interface. Category changes preserve splits, signed amounts, evidence and period guards. Ambiguous cases enter review. The operator selected one shared API key with the same frontend workflow access, without application logins, per-key scopes or an extra agent-only approval requirement.
- Category history and safe undo are available. Stale requests cannot overwrite intervening changes.
- User-facing journeys are exercised with generated fixtures, including two members, shared and personal accounts, errors and mobile layouts. Actual provider authorization and physical-device acceptance are separate evidence.
- Canonical lint, tests, build and smoke gates run on the exact candidate. Known failures are not silently relabeled as a pass.

## Boundaries

Keep the production checkout clean. Preserve the existing candidate worktree. Do not read credentials or private financial records, mutate provider connections, deploy production, commit or push as part of local implementation.

Real bank connections require the operator's Plaid Production Transactions entitlement and supported institutions. Production credentials, institution login and a partner's consent cannot be replaced by generated acceptance fixtures.

## Work order

1. Inventory canonical ledger, API/CLI and existing bank-feed contracts.
2. Finish the existing account-editor and recovery-focus fixes.
3. Apply the density system to canonical app pages, not only the sandbox shell.
4. Expose the machine interface over shared services, including remote queries, category proposals and the existing decision/undo workflow with shared-key authority.
5. Design and implement the production connector seam without converting the sandbox database into ledger authority or bypassing reconciliation.
6. Run integrated generated journeys and independent review before final gates and any separately authorized rollout.

## Concurrency

Resolve backend contracts before coding consumers. UI work may change canonical templates and scoped styles but must not edit the current onboarding JavaScript or its tests. Machine-interface work owns separate API/service/CLI tests. One owner changes the connector persistence and reconciliation seam. Freeze producers before integration gates. Avoid parallel builds that share output directories.

Real-bank onboarding and daily spending before a statement arrives require a first-class bank-feed reconciliation subject. A corroboration-only connector is a useful smaller capability but does not satisfy the complete requested workflow. Its observations must never impersonate a complete monthly statement.
